# Передача бэкендеру: фронтенд и интеграция, 16.09.2026

## Статус и границы

Локальная работа без коммита и PR разрешена фронтендером. Папки backend, infra, load и контракт не редактировались. Изменения общих документов не считаются согласованным ADR или принятым PR.

Прочитаны архитектура, контракт, план, документация страниц, README и инструкции потоков; проверены схемы, маршруты и сервисы API v0. Сгенерированы типы OpenAPI, подключены HTTP-клиент, TanStack Query, Keycloak PKCE и MSW. Основные экраны используют API-форматы вместо старого localStorage-демо. Основа работ: строка фронтенда 16.09 в PLAN, FR-01, FR-02, FR-10, FR-11.

## Замечания и вопросы для следующих задач бэкенда

1. **Обязательные документы, FR-02.** В backend/app/modules/workflow/defaults.py у этапов есть required_document_types, но создаваемые StageTransitionRule оставляют requires_attachment=false. В v0 можно уйти с подписания без файла. Нужно согласовать с архитектурой момент блокировки, тип документа и будущий API загрузки. Фронтенд следует allowed_transitions; при requires_attachment=true отправка блокируется до появления загрузки. Правила на клиенте самостоятельно не изменены.
2. **Момент сигнала об отсутствии документа.** backend/app/modules/radar/rules.py создаёт missing_document после половины нормы и проверяет документы текущего этапа. В архитектуре описано отсутствие обязательного документа без этого порога. Просьба подтвердить поведение и отразить его в источнике требований; также уточнить судьбу отсутствующего документа после перехода.
3. **Период в фильтрах.** В архитектуре упоминаются period_from/period_to, в контракте списка взаимодействий их нет. Контролы периода пока не добавлены. Нужен согласованный контракт с определением даты, по которой фильтровать.
4. **Ошибки OpenAPI.** backend/app/core/errors.py описывает Problem через model без явного application/problem+json, хотя фактический обработчик возвращает этот media type. Декларация POST transitions перечисляет не все возможные бизнес-ошибки сервиса, включая требования вложений и недопустимый переход. Просьба дополнить декларации и повторно экспортировать контракт. Клиент читает Problem независимо от этих двух JSON media types.
5. **Статус взаимодействия.** Просьба подтвердить правила завершения и паузы: наличие allowed_transitions и смена stage сами по себе не означают перевод status в completed. Фронтенд отключает смену этапа у неактивных записей, статус самостоятельно не вычисляет.
6. **Источник нормы.** Для объяснения сигнала желательно явно передавать источник нормы: ручной или статистический. Сейчас evidence содержит дни и норму, но не гарантированный типизированный источник. Фронтенд показывает серверное сообщение, не придумывает происхождение нормы.
7. **Документация.** frontend/AGENTS.md отсутствует. DAY_01 описывает раннее состояние без согласованного API; DESIGN и FRONTEND_PAGES содержат прежнее оформление. Пользователь отдельно подтвердил возврат скруглений и Montserrat. Актуальный запуск описан в frontend/README.md. Общие источники потребуется синхронизировать отдельным совместно проверенным изменением.
8. **CI.** Фронтенд должен проверяться также при изменениях contracts/**. Сейчас npm test включает api:check, но фильтр путей frontend workflow не охватывает контракт. Предлагается отдельная shared-задача, без ослабления проверок.

Это список вопросов и наблюдений по коду, а не согласованные изменения бизнес-правил. Отсутствующие возможности не реализованы в обход контракта.

## Предложение для ADR о зависимостях

Для совместного PR предлагается зафиксировать: keycloak-js как официальный OIDC-клиент вместо самописного протокола; openapi-typescript как генератор типов вместо ручной копии схем; MSW как HTTP-моки, использующие тот же клиент, что настоящий API. Существующие пакеты не реализуют эти задачи. Зависимости добавлены локально; запись ADR в ARCHITECTURE требует совместного рассмотрения. Prettier используется для воспроизводимого форматирования генерируемого файла.

## Совместный smoke-тест

Бэкендер запускает инфраструктуру, миграции, seed и API по backend/README.md. Фронтендер запускает VITE_AUTH_MODE=dev npm run dev и проверяет /me, радар, список, карточку, переход и чужую запись. Затем VITE_AUTH_MODE=keycloak npm run dev: вход в radar-web, профиль, обновление токена и выход. Для конфликта открыть одну карточку в двух вкладках, сохранить переход в первой, затем во второй; ожидать 409 и предложение обновить карточку без повторной автоматической записи. После этого можно считать совместную интеграцию проверенной и оформлять Issue/PR с результатами.
