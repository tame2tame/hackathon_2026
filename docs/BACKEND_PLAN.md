## Как идём

**Критический путь к демо «4 акта»:** импорт (B-10) → радар с нормами и SSE (B-12) → смена ответственного (B-08) → вложения (B-09) → метрики (B-11, B-14) → рейтинг (B-15) → отчёты (B-13) → редактор workflow (B-16a).

**Параллельные линии.** Один человек ведёт несколько агентов; у каждой линии свои модули, поэтому ветки разных линий не конфликтуют.

Общие файлы — `app/main.py`, `app/models.py`, миграции, `contracts/openapi.yaml` — меняются короткими правками и мёржатся по очереди.

### B-12. Радар: расписание, нормы, SSE — 20–22.09, линия A

- **Зачем:** NFR-02 (без перезагрузки); акт 3 демо; подсказки норм.
- **Контракт:**
  - `GET /api/v1/events` — `text/event-stream`, токен в заголовке `Authorization`, поддержка `Last-Event-ID`; события `interaction.transitioned`, `signal.opened`, `signal.resolved`, `import.applied`, `report.updated`;
  - `GET /api/v1/signals/summary` — матрица «КАМ × вид сигнала» для тепловой карты руководителя;
  - `GET /api/v1/workflows/default/norms`, `PUT .../norms/{stage_code}`, `POST .../norms/{stage_code}/accept-suggestion`.
- **Логика:**
  - воркер arq (`app/worker.py`): полный пересчёт сигналов в 03:00 МСК; ночью — подсказки норм: медиана и 80-й перцентиль завершённых этапов, если наблюдений не меньше 5;
  - события пишутся в Redis Stream с ограничением длины; поток SSE отдаёт пользователю только события его области видимости; heartbeat раз в 15 секунд.
- **Зависимости:** `redis`, `arq`.
- **Готово, когда:** событие перехода приходит руководителю команды и не приходит КАМу другой команды; переподключение с `Last-Event-ID` досылает пропущенное; тесты расчёта медианы; ночной пересчёт открывает и закрывает сигналы.
- **Результат 16.09 — выполнено.** В контракте `GET /api/v1/events` (`text/event-stream`, `Last-Event-ID`, пульс раз в 15 секунд), `GET /api/v1/signals/summary`, а также нормы: `GET /api/v1/workflows/default/norms`, `PUT .../norms/{stage_code}` и `POST .../norms/{stage_code}/accept-suggestion` — менять норму может руководитель или администратор, КАМ получает `AUTH_FORBIDDEN`. События публикуются при одиночном и групповом переходе (`interaction.transitioned`), при пересчёте радара (`signal.opened`, `signal.resolved`) и при применении импорта (`import.applied`); у каждого события есть владелец записи, по нему поток фильтруется: КАМ видит свои, руководитель — команду, администратор — всё, общие события идут руководителю и администратору. Транспорт — поток Redis с ограничением длины 1000 (`app/core/events.py`); без Redis та же логика работает в памяти процесса, поэтому тесты и CI не требуют внешних служб. ### B-21. Workflow по ответам жюри — 17–18.09

### Ревью B-21 — B-27 — 17.09

Независимое ревью всего пакета нашло десять замечаний; исправлены все, на каждое есть тест
(13 новых, всего 262). Главное:

- **Очередь обмена теряла изменение.** Строки очереди были заблокированы на время сетевого вызова,

- **Отчёт из воркера не учитывал правила доступа.** `CurrentUser` собирался без них, а именно этот

- **Очередь уведомлений могла застрять.** Вся пачка шла одной транзакцией: любая ошибка, кроме

  любой сбой отправителя становится обычным отказом, у запуска есть предел времени, а перенос
  строки в названии этапа больше не проходит проверку схемы.
- **Запрет по вузу прятал все записи B2C.** У них вуза нет, и условие `NOT (university_id = X)`
  давало NULL. Заменено на `IS NOT DISTINCT FROM`.
- **Эскалация и уведомления игнорировали область видимости.** Теперь получатели фильтруются так же,
  как списки, а если запись закрыта руководителю — уведомление уходит администраторам.
- **Во внешние каналы уходили персональные данные.** Telegram, Max и почта получают только заголовок
  события и ссылку.
- **Через настройку канала можно было увести секрет.** Адрес сверяется с `NOTIFY_ALLOWED_HOSTS`,
  смена адреса отвязывает секрет, пароль SMTP не уходит без STARTTLS.
- **Контакты организаций читал кто угодно без аудита.** Теперь их видит только тот, кто работает
  с клиентом, каждый просмотр пишется в аудит, а ИНН из 12 цифр (ИП и физлица) в организации
  не принимается.
- **Публикация процесса не защищалась от повторного нажатия.** Черновик и действующая схема берутся
  под блокировку, записи переносятся под `FOR UPDATE`, а создание записи ждёт конца публикации.
- **Групповой переход слал владельцу по уведомлению на запись.** Стала одна сводка.

Открытые вопросы ревью, оставленные сознательно и записанные в документах: `INTERACTION_DUPLICATE`
подтверждает существование чужой записи (иначе дубль нельзя объяснить), группа не ограничивает тип
контрагента, а документ обмена передаёт имя частного лица в LMS и CMS — без этого зачисление
на обучение невозможно.

## Как ставить задачу агенту

```markdown
**Задача:** B-09 Вложения
**Требования:** FR-03
**Контракт:** какие методы добавить или изменить — сначала contracts/openapi.yaml
**БД:** нужна ли миграция
**Готово, когда:** тесты из раздела задачи в docs/BACKEND_PLAN.md
**Не трогать:** frontend/, e2e/, модули других линий
```

- Одна задача — одна ветка — один PR; в PR не больше одной миграции.
- Перед мёржем: ребейз на `main`, `make check`, `make openapi` при изменении API, у Alembic одна голова.
- Архитектурное решение по ходу задачи — запись ADR в ARCHITECTURE.md в том же PR.
