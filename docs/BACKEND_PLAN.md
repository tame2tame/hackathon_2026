## Как идём

**Критический путь к демо «4 акта»:** импорт (B-10) → радар с нормами и SSE (B-12) → смена ответственного (B-08) → вложения (B-09) → метрики (B-11, B-14) → рейтинг (B-15) → отчёты (B-13) → редактор workflow (B-16a).

**Параллельные линии.** Один человек ведёт несколько агентов; у каждой линии свои модули, поэтому ветки разных линий не конфликтуют.

Общие файлы — `app/main.py`, `app/models.py`, миграции, `contracts/openapi.yaml` — меняются короткими правками и мёржатся по очереди.

### B-12. Радар: расписание, нормы, SSE — 20–22.09, линия A

- **Зачем:** NFR-02 (без перезагрузки); акт 3 демо; подсказки норм.
- **Контракт:**
  - `GET /api/v1/events` — `text/event-stream`, токен в заголовке `Authorization`, поддержка `Last-Event-ID`; события `interaction.transitioned`, `signal.opened`, `signal.resolved`, `import.applied`, `report.updated`;
  - `GET /api/v1/signals/summary` — матрица «КАМ × вид сигнала» для тепловой карты руководителя;
  - `GET /api/v1/workflows/default/norms`, `PUT .../norms/{stage_code}`, `POST .../norms/{stage_code}/accept-suggestion`.
- **Логика:**
  - воркер arq (`app/worker.py`): полный пересчёт сигналов в 03:00 МСК; ночью — подсказки норм: медиана и 80-й перцентиль завершённых этапов, если наблюдений не меньше 5;
  - события пишутся в Redis Stream с ограничением длины; поток SSE отдаёт пользователю только события его области видимости; heartbeat раз в 15 секунд.
- **Зависимости:** `redis`, `arq`.
- **Готово, когда:** событие перехода приходит руководителю команды и не приходит КАМу другой команды; переподключение с `Last-Event-ID` досылает пропущенное; тесты расчёта медианы; ночной пересчёт открывает и закрывает сигналы.
- **Результат 16.09 — выполнено.** В контракте `GET /api/v1/events` (`text/event-stream`, `Last-Event-ID`, пульс раз в 15 секунд), `GET /api/v1/signals/summary`, а также нормы: `GET /api/v1/workflows/default/norms`, `PUT .../norms/{stage_code}` и `POST .../norms/{stage_code}/accept-suggestion` — менять норму может руководитель или администратор, КАМ получает `AUTH_FORBIDDEN`. События публикуются при одиночном и групповом переходе (`interaction.transitioned`), при пересчёте радара (`signal.opened`, `signal.resolved`) и при применении импорта (`import.applied`); у каждого события есть владелец записи, по нему поток фильтруется: КАМ видит свои, руководитель — команду, администратор — всё, общие события идут руководителю и администратору. Транспорт — поток Redis с ограничением длины 1000 (`app/core/events.py`); без Redis та же логика работает в памяти процесса, поэтому тесты и CI не требуют внешних служб. Подсказка нормы — медиана и 80-й перцентиль завершённых этапов при пяти и более наблюдениях; для перцентиля добавлено поле `suggested_percentile_days` (миграция `8e758533e133`). Ночные задачи выполняет `app/worker.py` на arq: пересчёт радара в 00:00 UTC (03:00 МСК) и подсказки норм в 00:20 UTC; в compose добавлен сервис `worker`. Матрица сигналов на демо-данных: у руководителя 7 сигналов (Анна — 5, Михаил — 2), КАМ видит только свою строку. 15 новых тестов, всего 113.
- **Не сделано в этой задаче:** поток через реальный Redis вживую не проверялся — тесты идут на реализации в памяти, стенд с Redis поднят. Событие `report.updated` появилось в B-13 вместе с отчётами.

### B-16a. Редактор workflow — 23–24.09, линия A

- **Зачем:** FR-02 (переименование статусов), FR-09; финал демо.
- **Контракт:** `POST /api/v1/workflows` — шаблон; `POST /api/v1/workflows/{template_id}/versions` — черновик копией опубликованной версии; `PATCH /api/v1/workflow-versions/{id}` — этапы, порядок, правила, документы; `PATCH /api/v1/stages/{id}` — переименование; `POST /api/v1/workflow-versions/{id}/publish` — с картой переноса «код этапа → этап».
- **Логика:** в опубликованной версии разрешено только переименование; публикация переносит открытые взаимодействия переходом с `source=migration`, старая версия получает статус `retired`; нормы сохраняются по коду этапа.
- **Новые коды ошибок:** `WF_VERSION_NOT_DRAFT`, `WF_MIGRATION_MAP_INCOMPLETE` — добавить в каталог ARCHITECTURE.md в том же PR.
- **Результат 17.09 — выполнено.** В контракте `POST /api/v1/workflows`, `POST /api/v1/workflows/{template_id}/versions`, `PATCH /api/v1/workflow-versions/{id}`, `PATCH /api/v1/stages/{id}` и `POST /api/v1/workflow-versions/{id}/publish`; редактирует руководитель или администратор, КАМ получает `AUTH_FORBIDDEN`. Черновик создаётся копией последней версии шаблона вместе с этапами и правилами, поэтому правка начинается не с чистого листа. В опубликованной версии структура неизменна — попытка изменить её отвечает `WF_VERSION_NOT_DRAFT`, и разрешено только переименование этапа, которое сразу видно в карточках. Публикация требует карту переноса для этапов, на которых стоят открытые записи: без неё `WF_MIGRATION_MAP_INCOMPLETE` с перечнем полей. При публикации открытые взаимодействия переезжают на новую версию переходом `source=migration`, прежняя версия становится `retired`, а нормы переживают смену версии, потому что привязаны к коду этапа. Оба новых кода добавлены в каталог `app/core/errors.py` и в ARCHITECTURE. 9 новых тестов, всего 159.
- **Решение по ходу.** При переносе дата входа на этап не сбрасывается: смена версии процесса — не работа по взаимодействию, и радар не должен из-за неё забывать про застрявшую запись.
- **Готово, когда:** переименование видно в карточках; публикация с неполной картой → ошибка; перенос пишет историю и не теряет сигналы лицензий.

## Как ставить задачу агенту

```markdown
**Задача:** B-09 Вложения
**Требования:** FR-03
**Контракт:** какие методы добавить или изменить — сначала contracts/openapi.yaml
**БД:** нужна ли миграция
**Готово, когда:** тесты из раздела задачи в docs/BACKEND_PLAN.md
**Не трогать:** frontend/, e2e/, модули других линий
```

- Одна задача — одна ветка — один PR; в PR не больше одной миграции.
- Перед мёржем: ребейз на `main`, `make check`, `make openapi` при изменении API, у Alembic одна голова.
- Архитектурное решение по ходу задачи — запись ADR в ARCHITECTURE.md в том же PR.
