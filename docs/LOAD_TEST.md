# Нагрузочный тест

Проверяем НФТ из ТЗ: интерфейс отвечает быстрее секунды при полусотне одновременных
пользователей (NFR-01, NFR-06) и выдерживает не меньше десяти параллельных отчётов (NFR-07).

## Что нужно

- Стенд с данными v1: `make db-up`, `make migrate`, `make seed-full` в `backend/`.
- API в режиме разработки — нагрузка ходит с заголовком `X-Dev-User`, без Keycloak:
  `APP_ENV=local AUTH_MODE=dev make run`.
- [k6](https://k6.io/docs/get-started/installation/): `brew install k6` на macOS,
  пакет `k6` из репозитория Grafana на Linux.

## Сценарии

| Файл | Что делает | Порог |
|---|---|---|
| [`load/k6-main.js`](../load/k6-main.js) | Пользователей столько, сколько сказано в `VUS` (по умолчанию 50): радар и матрица сигналов, список взаимодействий, карточка, заметка, рейтинг. Разгон 30 с, полка 2 мин, спад 30 с | `p95 < 1000 мс`, доля ошибок < 1 % |
| [`load/k6-reports.js`](../load/k6-reports.js) | 10 пользователей заказывают отчёты в xlsx, json, pdf и xls одновременно | все задания доходят до `done`, `p95 < 30 с` |

Запуск:

```bash
k6 run -e BASE_URL=http://127.0.0.1:8000 load/k6-main.js
k6 run -e BASE_URL=http://127.0.0.1:8000 -e VUS=300 load/k6-main.js
k6 run -e BASE_URL=http://127.0.0.1:8000 load/k6-reports.js
```

### Что нашлось

- **Отчёты требуют живого воркера.** Первый прогон показал 0 из 10 готовых: задания уходили в
  очередь arq, а воркер не был запущен. Это не дефект кода, но именно так это выглядит на стенде,
  если воркер упал, — поэтому в [`docs/ADMIN_GUIDE.md`](ADMIN_GUIDE.md) есть отдельный пункт про
  зависшие в `queued` отчёты.
- **Дефект в самом сценарии.** `k6-reports.js` проверял состояние отчёта сразу после создания,
  хотя отчёт строится в фоне. Исправлено: сценарий опрашивает состояние до `done` или `failed`.
- **Хвост 5,71 с** при 50 пользователях. Отдельные запросы на этих данных быстрые — рейтинг 131 мс,
  матрица сигналов 32 мс, список из 50 записей 52 мс, воронка 23 мс, — поэтому хвост даёт не
  тяжёлый запрос, а конкуренция: каждая заметка в сценарии пересчитывает сигналы взаимодействия
  в одной транзакции. Порог выдержан, поэтому трогать это сейчас не стал; если понадобится
  запас — пересчёт после заметки можно увести в воркер.

Оптимизации не потребовались: оба порога НФТ выдержаны без изменений в коде.

## 300 пользователей и что дальше

Жюри просило не только цифру по НФТ, но и рассказ о масштабировании на 300+ пользователей.
Проверяли на том же ноутбуке: 8 ядер, 8 ГБ памяти, PostgreSQL, Redis и MinIO в Docker, k6 —
там же. Данные v1, между прогонами заметки нагрузочного сценария удалялись и делался
`VACUUM ANALYZE`, иначе каждый следующий прогон шёл по более толстой таблице.

| Пользователей | Копий API | p95 | Запросов/с | Ошибок |
|---|---|---|---|---|
| 50 | 1 | **386,59 мс** ✔ | 116,6 | 0 из 21 048 |
| 100 | 4 | 1,15 с ✘ | 138,5 | 0 из 24 996 |
| 300 | 1 | 2,19 с ✘ | 202,8 | 0 из 36 684 |
| 300 | 4 | 1,87 с ✘ | 226,4 | 0 из 40 872 |

**Ошибок нет нигде.** Система не отказывает и не теряет запросы — она замедляется: под нагрузкой
растёт очередь, а не доля пятисотых. Это важнее самой цифры p95: отказ пришлось бы чинить,
замедление лечится железом.

**Упирается не API, а база.** На 100 пользователях PostgreSQL в контейнере занимает **420 % CPU**
(четыре ядра из восьми), Redis — 6 %. Поэтому четыре копии API вместо одной дают всего +12 %
пропускной способности: копии ждут одну и ту же базу, которая делит процессор с ними и с самим k6.
На пустом стенде каждый метод отвечает за 11–36 мс — ни одного медленного запроса нет, вся
задержка под нагрузкой это конкуренция за ресурсы одной машины.

### Что делать для 300+ на настоящем стенде

По убыванию отдачи:

1. **Разнести по машинам.** Сейчас база, приложение и генератор нагрузки делят восемь ядер.
   Отдельный сервер (или управляемый PostgreSQL) под базу — самый большой прирост из всех пунктов
   и единственный, который ничего не меняет в коде.
2. **PgBouncer в режиме transaction.** 300 пользователей на нескольких копиях API — это сотни
   соединений; пул на стороне базы дешевле, чем соединение на каждый процесс.
3. **Копии API за nginx.** Приложение без состояния: сессии в токене, файлы в S3, кэш и события
   в Redis — добавляется копиями без липких сессий (проверено: `--workers 4` работает как есть).
4. **Копии воркера.** Очереди обмена и уведомлений захватываются арендой `locked_until`
   и `SKIP LOCKED`, поэтому вторая копия не отправит то же самое дважды.
5. **Пересчёт сигналов после заметки — в воркер.** Сейчас заметка пересчитывает радар записи
   в той же транзакции; при полусотне пользователей это незаметно, при трёхстах — самая частая
   запись в базу. Вынос в очередь убирает её из времени ответа.
6. **Реплика для чтения.** Отчёты, рейтинг и статистика читают много и не требуют последних
   миллисекунд — их можно увести на реплику, оставив мастеру работу КАМов.

Кэш готовых ответов (ADR-022) и файлы в S3 уже сделаны и работают на любой из этих конфигураций.

**Чего мы не проверяли:** 300 пользователей на настоящем сервере — сервера нет. Цифры выше
показывают поведение системы и место узкого горлышка, а не мощность будущего стенда.

## Куда смотреть, если порог не выдержан

- **Списки взаимодействий и сигналов.** Фильтры уже идут по индексированным полям
  (`ix_interaction_owner_status`, `ix_interaction_stage_entered`), но связанные сущности
  подтягиваются через `joinedload`: при росте страницы проверить план запроса и при
  необходимости перейти на `selectinload`.
- **Рейтинг.** Агрегаты по `program_metric` считаются на лету (B-15). Если именно они дают
  просадку — материализованное представление `mv_program_metric_month` и кэш в Redis по
  параметрам запроса, со сбросом после импорта и синхронизации.
- **Отчёты.** Строятся в воркере; узкое место обычно не в SQL, а в рендере файла. Помогает
  предел строк (50 000, уже есть) и запись xlsx в режиме `write_only` (уже есть).
- **События SSE.** Поток читает Redis с блокировкой; при большом числе подключений смотреть
  на число открытых соединений, а не на время запроса.
