# Нагрузочный тест

Проверяем НФТ из ТЗ: интерфейс отвечает быстрее секунды при полусотне одновременных
пользователей (NFR-01, NFR-06) и выдерживает не меньше десяти параллельных отчётов (NFR-07).

## Что нужно

- Стенд с данными v1: `make db-up`, `make migrate`, `make seed-full` в `backend/`.
- API в режиме разработки — нагрузка ходит с заголовком `X-Dev-User`, без Keycloak:
  `APP_ENV=local AUTH_MODE=dev make run`.
- [k6](https://k6.io/docs/get-started/installation/): `brew install k6` на macOS,
  пакет `k6` из репозитория Grafana на Linux.

## Сценарии

| Файл | Что делает | Порог |
|---|---|---|
| [`load/k6-main.js`](../load/k6-main.js) | 50 пользователей: радар и матрица сигналов, список взаимодействий, карточка, заметка, рейтинг. Разгон 30 с, полка 2 мин, спад 30 с | `p95 < 1000 мс`, доля ошибок < 1 % |
| [`load/k6-reports.js`](../load/k6-reports.js) | 10 пользователей заказывают отчёты в xlsx, json, pdf и xls одновременно | все задания доходят до `done`, `p95 < 30 с` |

Запуск:

```bash
k6 run -e BASE_URL=http://127.0.0.1:8000 load/k6-main.js
k6 run -e BASE_URL=http://127.0.0.1:8000 load/k6-reports.js
```

### Что нашлось

- **Отчёты требуют живого воркера.** Первый прогон показал 0 из 10 готовых: задания уходили в
  очередь arq, а воркер не был запущен. Это не дефект кода, но именно так это выглядит на стенде,
  если воркер упал, — поэтому в [`docs/ADMIN_GUIDE.md`](ADMIN_GUIDE.md) есть отдельный пункт про
  зависшие в `queued` отчёты.
- **Дефект в самом сценарии.** `k6-reports.js` проверял состояние отчёта сразу после создания,
  хотя отчёт строится в фоне. Исправлено: сценарий опрашивает состояние до `done` или `failed`.
- **Хвост 5,71 с** при 50 пользователях. Отдельные запросы на этих данных быстрые — рейтинг 131 мс,
  матрица сигналов 32 мс, список из 50 записей 52 мс, воронка 23 мс, — поэтому хвост даёт не
  тяжёлый запрос, а конкуренция: каждая заметка в сценарии пересчитывает сигналы взаимодействия
  в одной транзакции. Порог выдержан, поэтому трогать это сейчас не стал; если понадобится
  запас — пересчёт после заметки можно увести в воркер.

Оптимизации не потребовались: оба порога НФТ выдержаны без изменений в коде.

## Куда смотреть, если порог не выдержан

- **Списки взаимодействий и сигналов.** Фильтры уже идут по индексированным полям
  (`ix_interaction_owner_status`, `ix_interaction_stage_entered`), но связанные сущности
  подтягиваются через `joinedload`: при росте страницы проверить план запроса и при
  необходимости перейти на `selectinload`.
- **Рейтинг.** Агрегаты по `program_metric` считаются на лету (B-15). Если именно они дают
  просадку — материализованное представление `mv_program_metric_month` и кэш в Redis по
  параметрам запроса, со сбросом после импорта и синхронизации.
- **Отчёты.** Строятся в воркере; узкое место обычно не в SQL, а в рендере файла. Помогает
  предел строк (50 000, уже есть) и запись xlsx в режиме `write_only` (уже есть).
- **События SSE.** Поток читает Redis с блокировкой; при большом числе подключений смотреть
  на число открытых соединений, а не на время запроса.
