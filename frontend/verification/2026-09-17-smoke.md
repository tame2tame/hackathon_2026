## Исправления

- Сгенерированы актуальные TypeScript-типы из существующего OpenAPI. До генерации `npm test` останавливался на `api:check`.
- Карточка не подменяет показанную версию при возврате фокуса вкладки и восстановлении сети. Ранее фоновое обновление меняло `expected_version`, нарушая ожидаемый сценарий проверки конфликта. Остальные списки сохраняют фоновое обновление.
- После HTTP 409 требуется явное обновление перед следующей попыткой записи.
- Официальный Rostelecom Basis заменяет используемые шрифты интерфейса. Исходные файлы команды сохранены. Брендбук по ссылке не удалось прочитать; дальнейшая сверка оформления отложена по указанию пользователя.

## Автоматические проверки

- До исправления новый регрессионный тест падал: после возврата фокуса ожидалась версия 1, получена 2.
- После исправления `npm test`: 22 теста, включая проверку контракта, реальный QueryObserver с MSW для двух вкладок, заголовки dev/Keycloak, PKCE-инициализацию и отказ при ошибке обновления токена.
- `npm run build`: TypeScript и production-сборка успешно выполнены. `git diff --check` без замечаний.
- Проверки Keycloak и двух настоящих вкладок выполнены браузером; MSW не использовался в живой проверке.
- Обновление и истечение настоящего токена по времени не проверялись ожиданием; этот путь покрыт unit-тестом с подменой Keycloak.
- CI, нагрузка, production-деплой, полный e2e всех будущих разделов не проверялись.

S-03 проверен локально: текущие realm, клиент, redirect и серверные профили подходят фронтенду. `expected_version` и `INTERACTION_VERSION_CONFLICT` работают. Изменения в backend, infra и API-контракте для этих сценариев не потребовались.

Ответы на предыдущие вопросы найдены в `docs/BACKEND_PLAN.md`: требования документов на выходе с этапов, порог отсутствия документа, статусы и источник нормы описаны бэкендом. Типы фронтенда обновлены по текущему контракту. Наличие методов в контракте не означает, что интерфейсы вложений, импорта и аналитики уже подключены: это отдельная следующая работа. S-01 (CI на изменение контракта) и S-02 (общая документация) здесь не изменялись.

## Как повторить проверку

1. Из корня: `docker compose -f infra/docker-compose.yml up -d postgres redis keycloak api`.
2. Загрузить демо-данные: `docker compose -f infra/docker-compose.yml exec -T api python -m scripts.seed`.
3. Во frontend: `VITE_AUTH_MODE=keycloak VITE_API_BASE_URL= npm run dev`. Войти каждым демо-пользователем; локальные пароли — в файле realm, в отчёт не копируются.
4. Открыть одну доступную карточку без требования вложения в двух вкладках до первого перехода. Сохранить в первой и второй. Ожидать 201 и 409; во второй явно обновить карточку.
5. Для dev, не меняя основной API: `docker compose -f infra/docker-compose.yml run -d --no-deps --name radar-vuzov-dev-check -p 127.0.0.1:8001:8000 -e AUTH_MODE=dev api uvicorn app.main:app --host 0.0.0.0 --port 8000`. Если контейнер с этим именем уже существует, используйте существующий.
6. Во frontend: `VITE_AUTH_MODE=dev VITE_API_BASE_URL=http://127.0.0.1:8001 npm run dev`. Проверить профиль, радар и переключение пользователя.
7. После проверки вернуть режим Keycloak. Не запускать два Vite на 5173 одновременно.

Итоговое локальное состояние: frontend/.env.local (игнорируется Git) настроен на Keycloak и основной API через Vite proxy. Сервисы compose и дополнительный dev API на 8001 оставлены запущенными.
