# Правила для агентов — «Радар вузов»

Документ для любых AI-агентов (Claude Code, Codex, Cursor) и людей, которые ими управляют. Прочитать перед каждой задачей.

## Источники правды

По убыванию приоритета:

1. Официальное ТЗ кейса №6 «ИТ Школа Ростелекома» (PDF у команды).
2. [`ARCHITECTURE.md`](ARCHITECTURE.md) — архитектура, модель данных, конвенции API, решения (ADR).
3. [`contracts/openapi.yaml`](contracts/openapi.yaml) — контракт API между потоками.
4. [`docs/PLAN.md`](docs/PLAN.md) — порядок работ, сроки, индекс требований.
5. [`docs/FRONTEND_PAGES.md`](docs/FRONTEND_PAGES.md) — формат страниц.

Уточнения жюри от 17.09 и решения по ним — [`docs/JURY_QA.md`](docs/JURY_QA.md); при расхождении
с ТЗ они уточняют, а не отменяют его.

Диаграммы связей, программно-аппаратной архитектуры и базы данных —
[`docs/architecture/DIAGRAMS.md`](docs/architecture/DIAGRAMS.md).

Справочные документы: [`docs/DATA_PROCESSING.md`](docs/DATA_PROCESSING.md) — как считаются радар,
нормы, рейтинг и импорт; [`docs/ADMIN_GUIDE.md`](docs/ADMIN_GUIDE.md) — эксплуатация;
[`docs/DEPLOY.md`](docs/DEPLOY.md) — стенд; [`docs/SECURITY.md`](docs/SECURITY.md) — меры защиты;
[`docs/LOAD_TEST.md`](docs/LOAD_TEST.md) — нагрузка.

Если документы противоречат друг другу или задаче — остановиться и спросить человека. Не выбирать молча.

## Потоки и владение

| Поток | Папки | Владелец |
|---|---|---|
| Бэкенд | `backend/`, `infra/`, `load/` | бэкендер и его агенты |
| Фронтенд | `frontend/`, `e2e/` | фронтендер и его агенты |
| Общее | `ARCHITECTURE.md`, `AGENTS.md`, `contracts/`, `docs/`, `.github/` | оба |

- Не изменять папку другого потока. Нужна правка у соседа — описать её в Issue.
- PR, который меняет общие файлы, одобряют оба человека.
- Инструкции потока лежат в его папке: [`backend/AGENTS.md`](backend/AGENTS.md), `frontend/AGENTS.md`.

## Как выполнять задачу

1. Задача — GitHub Issue с меткой потока (`stream:backend`, `stream:frontend`, `stream:shared`) и номером требования из индекса в `docs/PLAN.md` (например `req:FR-02`).
2. Ветка `<поток>/<номер-issue>-<кратко>`, например `backend/12-transitions`. В `main` не коммитить.
3. **Контракт первым.** Новый или изменённый метод API сначала появляется в `contracts/openapi.yaml`, потом реализуется и подключается.
4. Каждое изменение сопровождается тестом. Баг — сначала падающий тест, потом исправление.
5. PR ссылается на Issue (`Closes #12`) и перечисляет, что проверено и какими командами.
6. **Задача готова**, когда CI зелёный и выполнены критерии приёмки из Issue. «Должно работать» без проверки не считается.

## Код

- Менять только то, что нужно задаче. Без попутных рефакторингов и переименований.
- Сложное место — короткий комментарий «почему», а не пересказ кода.
- Секреты, токены и пароли — только через переменные окружения; пример в `.env.example`. Никогда в коде, логах и тестовых снимках.
- Только синтетические данные. Реальных персональных данных в репозитории, фикстурах и на демо-стенде нет.
- Интерфейс, документация и тексты ошибок — на русском. Идентификаторы, коды ошибок, ветки и коммиты — на английском.
- Коды ошибок берутся из каталога в `ARCHITECTURE.md`; новый код добавляется туда в том же PR.
- Новая зависимость — только если задачу не решает стандартная библиотека или уже подключённый пакет; причина в описании PR.

## Архитектурные решения

Решение, которое меняет архитектуру — новый сервис, библиотеку, таблицу, модель данных, формат API, — фиксируется записью ADR в разделе «Решения» `ARCHITECTURE.md` в том же PR.

## Безопасность (152-ФЗ, приказ ФСТЭК №117)

- Права проверяет только сервер. Фронтенд лишь скрывает недоступное.
- Каждый эндпоинт с данными взаимодействий имеет тест «чужая запись недоступна».
- Персональные данные не попадают в логи и тексты ошибок.
- История переходов и журнал аудита только дописываются.

## Без решения человека нельзя

- Пушить в `main`, мёржить собственные PR, менять защиту веток и настройки репозитория.
- Создавать облачные ресурсы, что-либо покупать, публиковать стенд или данные.
- Удалять или переписывать применённые миграции; удалять данные.
- Отключать или ослаблять проверки CI, помечать тесты пропущенными ради зелёного статуса.

## Проверки перед PR

- Бэкенд: команды из [`backend/AGENTS.md`](backend/AGENTS.md).
- Фронтенд: `npm test && npm run build` в `frontend/`.

В отчёте о задаче честно указать, какие проверки запускались и с каким результатом, и что осталось непроверенным.
